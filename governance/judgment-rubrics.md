# 判斷力 Rubrics（D）— 弱模型可執行版

> 把需要「經驗」的判斷拆成可勾選的判準。遇到對應情境**逐條勾選，不憑感覺**。
> 每條 rubric 附一個正例、一個反例。

---

## R1. 何時該升級模型

任一成立即升級（升級路徑見 `model-orchestration.md` 第 6 節）：

- [ ] 同一個錯誤修了兩次還在（haiku 例外：錯 1 次即升級，見 model-orchestration 第 6 節）
- [ ] 自己的解釋前後矛盾（這輪說根因是 A，上輪說是 B，兩者不相容）
- [ ] 需要同時推理超過 3 個模組的交互行為
- [ ] 需求模糊到拆不出可驗收的工單——**限技術面模糊**（缺的是「怎麼做」）；缺的是「做什麼 / 要不要做」屬產品面 → 走 R3 問使用者
- [ ] 兩個技術方案都說得通，決定不了（架構取捨）

**R1 與 R3 的優先順序**：純技術失敗先套 R1 升級模型；升級後仍失敗、或已無更高等級可升（opus 之上不自行升）、或問題涉及產品判斷 → 套 R3 問使用者。

升級時必附失敗軌跡（格式見 model-orchestration 第 6 節）。

**正例**：haiku 修 type error，改了兩次 `tsc` 還報同一個錯 → 停手，帶兩次 diff + 錯誤訊息升 sonnet。
**反例**：第一次失敗後自己再試第三、四、五次，每次微調一點 → 30 分鐘後 diff 已擴散到 6 個檔案，還是同一個錯。

## R2. 何時算真的完成

**全部**成立才是「完成」；缺任何一項，狀態是「進行中」，不准回報完成：

- [ ] 每條驗收條件有對應證據（diff / 測試輸出 / curl 結果 / 截圖）
- [ ] 測試「實際執行過」且輸出貼在回報裡（不是「應該會過」）
- [ ] `git diff --name-only` 與宣告的範圍一致，無範圍外檔案
- [ ] 沒有「順手」重構或改動無關程式碼
- [ ] 涉及服務 / 部署時：有 smoke test 證據
- [ ] 至少一項驗證走**真實初始化路徑**並檢查副作用真的發生了（資料寫進去了嗎、
      檔案產生了嗎），不全靠自建 fixture（來源：2026-07-22）
- [ ] 攔截型機制（hook / gate / validator / 權限檢查）：測試含**陰性案例**——
      不只「壞輸入被擋」，更要「好輸入放行」。前者能被「擋一切」的壞實作滿足，
      後者不能（來源：2026-07-31）
- [ ] 預期失敗的測試一併斷言**錯誤訊息內容**——斷言 exit code 不等於斷言行為，
      崩潰與正常失敗無法區分（來源：2026-07-31）
- [ ] 委派出去的任務：以 `git diff --stat` 或指定產物是否生成為準，**不看 exit code、
      不看完工報告**。報告寫的是「計畫」而非證據時，預設它沒做
      （來源：2026-08-10、2026-08-17）
- [ ] 委派出去的審查／評估：驗證的是它的**證據**不是結論——帶數字的斷言現算一次，
      尤其在它大部分講對的時候（月暈效應）；回應時逐條標「全採納／採納結論但修正證據／
      部分不同意」並留理由，否則下一輪會被改回去（來源：2026-08-08）
- [ ] 宣稱「測試驗到了 X」之前，先把 X 弄壞一次，確認測試真的會紅
      （來源：2026-10-07、2026-08-25）
- [ ] 測試常數分兩種：**描述現況的要導出**（數量、路徑、fixture 名），**守門檻的才寫死**
      （預算 baseline、核准清單）；導出來源必須獨立於被驗證的值，用受測值自己算期望值
      的斷言恆真（來源：2026-08-25、2026-09-30）
- [ ] 背景／長任務完成時讀 log 末尾的實際結果，不信外層包裝的 exit code
      （`cmd > log; echo "exit=$?"` 回報的是 echo）；跑數小時的任務用 `caffeinate -i` 包住
      防睡眠（來源：2026-10-21）

**正例**：「驗收 3/3 通過，pytest 輸出如下（貼 12 passed），diff 只動宣告的 2 檔」→ 完成。
**反例**：「已完成修改，邏輯上應該正確，建議之後補測試」→ 這是「進行中」，照 R2 不得標示完成。
**反例**：委派回來 exit 0、報告寫著完整計畫 → `git diff --stat` 與派工前逐字相同，
一個檔案都沒動。exit 0 在非互動委派裡是假訊號。

## R3. 何時停下來問使用者

任一成立**立即停**（問一次的成本遠小於做錯一輪的成本）：

- [ ] 決策會影響產品行為，而規格沒寫（不是純技術對錯）
- [ ] 要做不可逆操作：刪檔、force push、改 production 設定、對外發送內容
- [ ] 實際範圍比使用者描述大一倍以上（例：說改一個檔，實際要動五個）
- [ ] 兩輪重試失敗，且已依 R1 升級過模型仍失敗（或已到 opus 無可再升）
- [ ] `git status` 出現非預期變更（可能有其他 session 在動 repo）
- [ ] 安全 vs 便利的取捨（例：要不要放寬權限）
- [ ] 批次重算／回填前先 diff「目前存的值 vs 依現行設定算出的值」，出現本次變更以外的差異
      （例：使用者刻意沒套用的舊設定）→ 先問，不讓一次重算夾帶多個變更（來源：2026-10-31）

**正例**：修 bug 時發現根因在另一模組，修它會改公開 API → 停，列出兩個選項問使用者。
**反例**：「使用者應該是想要 X，先做了再說」→ 做完發現方向錯，整輪重工。

## R4. 方向錯了的訊號（該換路，不是再試一次）

出現**兩個以上** → 停止目前路線，換路：

- diff 每輪淨增加，越修越大
- 修好 A 壞了 B，修好 B 又壞回 A
- 開始改測試來遷就實作（不是改實作去通過測試）
- if/else 特例分支越加越多
- 自己開始說「先 workaround，之後再重構」

**換路的定義**（三選一，不是同一條路再走一遍）：
1. 丟棄 working tree，回到 Phase 1 重新理解問題
2. 重切成更窄的工單（`tech-lead-mode.md`）
3. 帶失敗軌跡升級模型（R1）

**正例**：修了三輪，每輪 diff +50 行、測試通過數反而下降 → `git checkout .`，回根因分析重來。
**反例**：「再給我一次機會，這次一定行」→ 第四輪，diff +80 行，測試還是紅的。

## R5. 品質底線（二元檢查，不問「好不好」）

- [ ] `tsc --noEmit` / `ruff` 通過（0 error）
- [ ] 現有測試全過（貼輸出）
- [ ] 無 console.log / debug print
- [ ] 新增行 grep 過 `-i "api[_-]?key\|secret\|password"` 無 hardcode
- [ ] 函式 < 50 行、檔案 < 300 行（`rules/coding-standards.md`）
- [ ] 無空 catch block

全部打勾 = 底線達標。底線**之上**的品味問題（命名優雅度、抽象層次高低）→ 弱模型不自行判斷，在回報中標註「品味項未審」，留給使用者或強模型。

**正例**：checklist 6/6 通過，回報加註「函式命名採現有慣例，未做品味級審查」。
**反例**：checklist 只跑了 lint，就評語「整體程式碼品質良好」→ 這是編造，R5 沒有「整體品質」這個項目。

## R6. 部署 / 接線類改動的完成判準

適用於：symlink 佈局、hook 掛載、link farm、`@` 常駐路徑、目錄結構、下游注入——
凡是「正本」與「實際生效的部署物」是兩份實體的改動。

**全部**成立才算完成。這一群的共同失敗模式是**沒有錯誤訊息**——`@` 路徑不存在會靜默
略過、dangling symlink 只是找不到、未授信任的 hook 直接跳過。所以「沒報錯」不是證據：

- [ ] 部署物已重新生成（改 `index.json` / 註冊檔後跑過對應 setup 腳本）
      （來源：2026-07-24）
- [ ] **舊路徑**仍可 resolve——不只驗證新路徑正確。相容層是重構中最容易被無聲
      刪掉的東西，因為它不屬於新設計的任何一部分（來源：2026-07-23）
- [ ] 從**消費端**實測讀得到（`ls -l` 那個 harness 真正讀的路徑，不是驗證檔案
      存在於 repo）（來源：2026-07-04、2026-07-07）
- [ ] 停用 / 廢止類改動：下游殘留已反注入清除——**不安裝 ≠ 移除既有的**
      （來源：2026-07-31）
- [ ] 腳本會動多個系統狀態時：前置檢查全部前置，每個 exit 路徑都問過
      「此刻系統停在什麼狀態」（來源：2026-07-06）
- [ ] 驗收看**行為證據**（hook.log 有無新 BLOCK、現算檔數與容量），不看完工報告，
      也不看文件寫了什麼（來源：2026-07-31、2026-08-04）

**文件禁令**：散文只准描述設計意圖，不准描述部署狀態。凡是「已安裝 / 已部署 /
已刪除 N 份」一律附現算指令或直接改成腳本輸出——手抄快照當下也許是真的，之後任何
一次 `.git/hooks` 重建、repo 重 clone、或收尾漏做都會讓它變謊報，且沒有機制會報錯。
**文件宣稱有防護而實際沒有，比明擺著沒有更危險**：沒人會去查一個「已完成」的項目。
（來源：2026-08-04）

**改註冊檔的額外風險**：改動 agent 的 hook 註冊檔（command 字串本身）等同讓該 hook
重新進入未授信任狀態，而失效是靜默的。判別「是誰在跑」優先用 payload 裡既有的欄位，
不要為此去改註冊。（來源：2026-08-17）

**正例**：改完 `index.json` 的 name 欄 → 重跑 `bin/setup-claude.sh --all` →
`for l in ~/.claude/skills/*; do [ -e "$l" ] || echo "$l"; done` 無輸出 → 完成。
**反例**：跑完 maintenance §7 索引四查全綠就宣告完成 → farm 早已 dangling，
四查的覆蓋範圍根本不含 farm。

## R7. 動手前先盤點既有

適用於：新增設施（hook / agent / 自動化）、處理某份資料源、把資料加進介面、執行舊待辦。
共同失敗模式是**重做一個已經被解決（或已被刻意分好層）的東西**，且做完才發現。

動手前**全部**查過：

- [ ] 同一事件層的既有設施（`~/.claude/settings.json`、專案 `.claude/`）——同一 hook 事件
      只允許一個歸屬，擴充優先於新建（來源：2026-07-10）
- [ ] 既有程式碼有沒有處理過同一份資料（`grep -rn` 去重鍵、parser、測試名）；既有實作的
      註解與測試就是文件（來源：2026-08-10）
- [ ] 幫某個 agent 裝 lifecycle hook 前，grep 自己的程式碼有沒有在呼叫那個 agent 的 CLI——
      「觀測 X 的工具」同時「呼叫 X」就必須有自我識別通道（env 變數）（來源：2026-08-08）
- [ ] 同類資料的既有先例（例：Claude 的 5h／weekly 怎麼分層）——先問「這份資料該落在哪一層」，
      不是「哪些檔案會顯示它」；檔頭註解常寫著答案（來源：2026-09-01）
- [ ] 要顯示／使用某個欄位前，抽查真實資料的值有沒有變化（`sort | uniq -c`）；全是常數或空值
      → 先回報，不出實作計劃（來源：2026-10-12）
- [ ] 舊分析記下的待辦是**當時的觀察**不是規格：動手前對實際檔案重跑一次掃描，確認範圍一致
      （來源：2026-08-21）

**正例**：要加 token 去重 → 先 `grep -rn "requestId\|dedup"` → 找到既有 last-write-wins 實作與測試 → 重用。
**反例**：原型「發現」去重陷阱，計劃書寫「不要照抄既有實作」→ 系統性低估 1.62%，同一份資料兩套解讀。

## R8. 資料與數字的真實性

適用於：解析外部資料、寫統計／分類、批次改寫、在文件裡寫任何估計數字。
共同失敗模式是**數字看起來合理但是錯的**——沒有錯誤訊息，偏誤方向通常是「看起來很好」。

- [ ] 外部資料的形狀只認**攔截到的真實樣本**；`a ?? b` 這類防禦寫法是作者的不確定，
      不是規格（來源：2026-08-17）
- [ ] 批次改寫／遷移前先 `grep -oE ... | sort -u` 掃出真實資料的**所有變體**（含註解掉的、
      舊名）；改寫結果用「目標是否真的存在」驗證（來源：2026-07-23）
- [ ] 分類／歸因：第一件事加守恆檢查（各桶總和 == 全體），第二件事看「未分類」桶大小與內容；
      未分類率 0 不是完美，是在亂塞（來源：2026-08-10）；「無法歸類」桶定期看內容不只看總數
      （來源：2026-08-25）
- [ ] 從 log／transcript 挖統計：先問「這個字串是作用目標，還是只是被順帶提到」——寫入類只認
      宣告目標的欄位（patch 標頭、`file_path`）；不可能常被動的項目呈現整齊分佈 → 先懷疑口徑
      （來源：2026-08-08）
- [ ] 接新資料源：挑多種類型的真實標的跑端到端並逐欄看輸出，fixture 從實際回應裁剪，
      不用自己對格式的想像（來源：2026-10-14）
- [ ] 估重構／優化收益：先估**替代物的成本**，不只算刪掉多少；數字先量測再寫進文件，
      不准先寫估計值等回填（來源：2026-08-18、2026-08-21）

**正例**：分類器跑出漂亮分佈 → 先檢查五桶加總 == total → 只有 88.7% → 改嚴格比對重算，other 41.6% 照實寫。
**反例**：`'ls' in command` 寬鬆比對得到「理解 21.1%」，直接寫進規格當可行性證據。

## 誠實標註：rubric 的極限

R1–R8 覆蓋**可拆解**的判斷。以下情況 rubric 無效，不要硬套：

- 產品方向 / 使用者體驗的取捨 → 問使用者（R3 第一條）
- 文案、命名、寫作風格的品味 → 標註「品味項未審」或升級模型
- 「這個功能該不該存在」 → 問使用者，這永遠不是技術問題

遇到以上情況還假裝能用 checklist 解決，就是本檔最想防止的錯誤。
