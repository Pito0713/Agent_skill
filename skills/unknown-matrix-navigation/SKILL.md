# 未知矩陣導航 (Unknown Matrix Navigation)

> 出處：Thariq Shihipar (Anthropic), "Field Guide to Fable", AI Engineer World's Fair 2026。
> 定位：**判斷程序**，不是任務流程。掛在 coding-workflow-core 的 Phase 1（理解）與 Phase 3（實作）之上，隨時可被重新觸發。

---

## 母原則：地圖不等於疆域

**Prompt 與計畫是地圖；codebase 與 runtime 才是疆域。**「未知」= 兩者的落差，而落差會在執行中不斷冒出來——不是接需求時分類一次就結束。

因此本 skill 有兩個觸發時機：

1. **接需求時**：對需求做一次四象限分類（§2）
2. **執行中**：任何時候疆域與地圖矛盾（schema 跟假設不符、模組不存在、測試揭露隱藏耦合）→ 該未知**已換象限**，停下來重新分類，禁止默默繞過去拼湊（呼應鐵律 4「卡住就停」）

---

## 1. 第零判斷：這個未知的答案在誰手上？

分類任何未知之前，先回答這一題——它決定你該「查」還是「問」：

| 答案位置 | 行動 | 絕對禁止 |
|---------|------|---------|
| **疆域裡**（codebase、docs、可實跑驗證） | 自己查：read / grep / 跑測試，查完直接變 Known | 拿去問使用者（伸手牌） |
| **使用者腦中**（意圖、偏好、業務規則、風險承受度） | 用 §2 的手段抽取（訪談或原型） | 自己腦補猜測後直接實作 |
| **還不在任何人腦中** | 用原型或盲點掃描把它「浮現」出來 | 假裝它不存在 |

> 這條是本 skill 對 AI 判斷力的核心貢獻：**大部分「模糊需求」其實是混合體**——先把能自查的部分查掉，剩下的才值得占用使用者的注意力。問題的品質，取決於你先消化了多少疆域。

---

## 2. 四象限分類與對應手段

三種抽取手段對應「答案的可抽取程度」：**問得出來 → 訪談；問不出來、看到才認得 → 極端原型；連問題都還不存在 → 盲點掃描**。

### A. 已知已知 (Known Knowns) — 需求明確

- **特徵**：需求具體、驗收標準清楚、技術路徑無歧義。
- **行動**：**直接執行，不追加確認。** 對已明確的事反覆問「你確定嗎」是過度限制（over-constraining），浪費使用者注意力也閹割自己的執行力。
- **邊界**：與鐵律 3「不猜意圖」不衝突——命中多個 skill 觸發詞或含模糊詞才問；單純明確的需求不屬於此類。

### B. 未知已知 (Unknown Knowns) — 使用者「看到才認得」

- **特徵**：涉及品味／美感／體感的需求（UI、Dashboard、互動、文案語氣），使用者說不出規格，但看到成品能立刻判斷喜不喜歡。
- **行動**：**極端原型 (Extreme Prototypes)**——一次給 4 個方向迥異的選項讓使用者「反應」，用對比抽取說不出口的偏好。
- **品質關卡**：4 個選項必須在**至少兩個維度**上走極端（如：密度×色彩、擬物×極簡），同款微調 4 次 = 失敗。禁止只給一個中規中矩的答案。

### C. 已知未知 (Known Unknowns) — 知道有沒想透的地方

- **特徵**：使用者（或你自己）能明確指出缺口：業務邏輯沒定、DB 結構不明、API 契約未知。
- **行動**（依序）：
  1. 先過 §1——答案在疆域裡的自己查掉
  2. 剩下的啟動**訪談模式 (Interviews)**：一次只問**一題**，且優先問「答案會改變架構走向」的問題；答案只影響細節的問題不值得問
  3. 或請使用者給**參考文獻 (References)**：「codebase 裡哪個檔案有類似邏輯？」→ 讀舊地圖畫新地圖
- **停止條件**：剩餘問題的答案不再改變架構 → 停止訪談，把假設**顯式列出**（「我假設 X、Y，若不對請指正」）然後動工。無限追問和悶頭亂做一樣糟。

### D. 未知未知 (Unknown Unknowns) — 最危險的象限

- **特徵**：使用者要在**他不熟悉的模組**上動工（「幫我接一個新的 auth provider」），連該問什麼都不知道。
- **行動**：寫任何 code 之前執行**盲點掃描 (Blindspot Pass)**：
  1. 掃描相關模組的實際結構（疆域）
  2. 產出**這個 codebase 特有的**盲點清單：隱藏耦合、既有慣例、安全邊界、會被波及的模組——泛用 checklist（「注意錯誤處理」）= 失敗，每一條都要指到具體檔案或機制
  3. **反向教學**：根據掃描結果，告訴使用者「接下來這樣下 prompt 會更準」——盲點掃描的產出就是更好的問題
- **與找 bug 的區別**：找 bug 是驗證地圖上有的東西；盲點掃描是把地圖上沒有的疆域畫出來。

### 多象限並發時的處理順序

**D → C → B**：先掃盲點（擴大地圖）→ 盲點產出的新問題進訪談（問對問題）→ 品味問題最後用原型收斂。順序反了會發生「訪談問錯問題」——因為你還沒看過疆域。

## 3. 對自己也適用：AI 的對抗自審 (Adversarial Self-Interrogation)

矩陣不是只用來分類使用者的未知——**你自己對疆域和意圖同樣有未知**。被動標記假設不夠，要主動出題攻擊自己的產出：

**時機**：動工前（進入不熟悉的模組時）＋ 結論成形後（回覆使用者前）。

**程序**：

1. **出題**：對自己的產出生成 2–3 個挑戰題。出題原則：專挑「如果我錯，最可能錯在哪」的位置——邊界條件、隱式假設、被我略過沒讀的檔案、「應該是這樣」的敘述
2. **作答並標注證據等級**：每個答案標明是「已驗證」（讀過碼／跑過測試）、「推論」（從已驗證事實推導）、還是「假設」（沒有證據）
3. **處置**：答不出來、或只有「假設」等級 → 那就是自我盲點 → 當場驗證；驗不了的在產出中**顯式標記為假設**交給使用者。禁止把「我沒查過」包裝成「應該是這樣」

**去相關階梯（關鍵限制）**：同一個 context 裡自問自答，出題者與作答者**共享同一套盲點**——產生錯誤的推理會照樣批准那個錯誤。所以 L1 只能抓表層，信心不足逐級升級：

| 層級 | 手段 | 為什麼有效 |
|------|------|-----------|
| L1 自問自答 | 上述程序，同 context 內 | 便宜，抓表層疏漏；**不能當終局驗證** |
| L2 疆域仲裁 | 實跑測試、實讀檔案、read-back | 疆域不共享你的盲點，是最便宜的異質對抗者 |
| L3 異質對抗 | 全新 context 的 subagent 或不同模型做對抗審查 | 高風險／大改動必做，去除推理相關性（呼應鐵律 2「驗證不自驗」） |

**與 §4 的分工**：§3 修 **AI 的未知**（產出正確性），§4 修**使用者的未知**（理解同步）。兩者不互相取代——把 §4 的測驗改成 AI 自考自答，人類就離開了迴圈，正是 Stay in the loop 要防的失敗。

---

## 4. 完工驗收：保持人類在迴圈中 (Stay in the Loop)

- **觸發**：跨 >3 檔案的重構、動到核心架構、或使用者看不到中間過程的大改動。小改動不觸發（過度儀式化會稀釋這個機制的效力）。
- **行動**：
  1. 不要只回「已完成」
  2. 產出**互動式報告**（HTML 或 Markdown）：變更的上下文（為什麼）、直覺邏輯（怎麼想的）、具體改動（動了什麼）
  3. **隨堂測驗 (Quizzes)**：報告最後出 1–3 題，考點必須是「答錯就代表接下來會做錯決策」的理解（如：改了哪個邊界條件、哪個模組現在依賴新行為），禁止考記憶題（「新函式叫什麼名字」）
  4. 使用者答對才算結案；答錯 → 針對錯的那題重新講解，不是重考
- **與鐵律 2 的關係**：測驗驗的是**人的理解**，不取代「驗證不自驗」——程式碼本身仍要實跑測試貼輸出。

---

## 5. 反模式（任一出現 = 本 skill 執行失敗）

- 把疆域裡查得到的答案丟給使用者（伸手牌訪談）
- 一次拋出一串問題清單（違反 one-question-at-a-time）
- 4 個原型只是同款微調
- 盲點掃描產出泛用 checklist 而非 codebase 特定發現
- 對已明確的需求反覆確認（過度限制）
- 執行中發現疆域與地圖矛盾，卻默默繞過去拼湊
- 未驗證的假設不標記，混進結論裡
- L1 自問自答通過就視為已驗證（出題者與作答者共享同一套盲點，終局驗證必須到 L2 以上）
- 把 §4 的人類測驗改成 AI 自考自答（人類離開迴圈）
- 測驗出成記憶題，或使用者答錯後直接放行
