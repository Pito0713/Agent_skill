# Mentor 共用協定（正本）

> **這份檔案在執行時不載入。** 五份 `mentor-*/SKILL.md` 各自內聯了本協定的壓縮摘要，
> 執行時照那份摘要做即可，不需要讀這裡。
>
> 本檔的用途有兩個：
> 1. **正本**——摘要寫得不夠清楚、或要確認某個格式的完整長相時，人或模型來這裡查。
> 2. **模板**——新增第六個 mentor 時，照 §8 把變數填進去，避免又從零抄一份。
>
> 非 skill package（無 frontmatter、無 SKILL.md），不進 `skills/index.json`，
> 不進任何 harness 的路由表，不被 link farm 掛載。
>
> 建立於 2026-08-18，見 `memory/project-context.md` ADR-022。

## 為什麼是「內聯摘要」而不是「執行時讀這份檔」

抽共用段落有兩種做法，token 帳完全不同：

| 做法 | 單次呼叫成本 | 說明 |
|------|------------|------|
| 引用式（SKILL.md 指向本檔，執行時必讀） | 幾乎不省 | 省下的 SKILL.md 體積，等額付回在讀共用檔上；要同 session 第二次 mentor 呼叫才開始賺 |
| **內聯壓縮（現行）** | **每份省 123–228 tok** | 共用段壓成 12 行摘要留在 SKILL.md，共用檔不進執行路徑 |

選內聯的關鍵理由：**被抽掉的段落絕大多數是「用一行描述就能正確執行的格式」**
（末行輸出長什麼樣、迷思怎麼開場、知識圖譜四個箭頭），不是需要逐字複製的規格。
真正需要逐字精確的只有 Phase 0 那行 vault 路徑，摘要裡直接寫死完整路徑即可。

**節省幅度要誠實記錄**（2026-08-18 實測，`bytes/3.5` 口徑）：

```
neuro   2902→2678 (-224)   tech    3352→3167 (-185)   science 3650→3422 (-228)
society 3504→3295 (-209)   invest  3719→3596 (-123)   合計 17127→16158 (-969)
```

規劃時預估每份省 350–400，實際只有 123–228。**差距的原因是摘要本身要價約 300 tok**——
要保住五個 domain 各自不同的關係詞、箭頭標籤、迷思符號、文獻來源，摘要就壓不下去。
被移除的共用段約 450–500，扣掉摘要淨值就只剩兩百上下。

因此**本次重構的主要價值不是省 token，是消除五份重複與建立新增 mentor 的模板**。
若日後要真正大幅瘦身，槓桿更大的是各 SKILL.md 裡的兩段純冗餘（見 §10），不是這裡。

**代價要說清楚**：五份摘要之間可能各自漂移，沒有任何機制會偵測。
改動協定時必須手動同步五份 + 本檔，見 §9。

## §1 Phase 0：讀取 Vault 上下文

原始完整版（各 mentor 曾各存一份）：

```bash
source "$HOME/Agent_skill/.env" 2>/dev/null
<DOMAIN_UPPER>_DIR="${OBSIDIAN_VAULT_PATH}/knowledge/<domain>"

EXISTING_NOTES=$(ls "$<DOMAIN_UPPER>_DIR"/*.md 2>/dev/null | xargs -I{} basename {} .md)

if [ -z "$EXISTING_NOTES" ]; then
  echo "📂 knowledge/<domain>/ 目前為空，從頭建立知識節點"
else
  echo "📂 使用者已有筆記："
  echo "$EXISTING_NOTES"
  echo "→ 確認：這些概念是否與當前問題相關？優先延伸，不重複。"
fi
```

**壓縮後等價於**：`ls "$OBSIDIAN_VAULT_PATH/knowledge/<domain>"/*.md`，有結果就進 §2，沒有就跳過 §2。

**上下文注入規則（共用四項）：**

```
[ ] 讀出現有筆記標題與標籤
[ ] 確認使用者已掌握哪些相關概念（已掌握 → 直接跳到進階層，不重講基礎）
[ ] 回覆中主動標注「你在 [[note-name]] 已記錄了 X，本次延伸 Y」
[ ] 當前問題與多個既有筆記交叉 → 優先說明節點間的連結關係
```

各 domain 額外一項，見 §8「Phase 0 附加規則」欄。

## §3 確定性四級（符號與等級名共用）

| 符號 | 等級 |
|------|------|
| ✅ | 高度確立 |
| ⚠️ | 合理推論 / 情境成立 |
| ❓ | 初步證據 / 待驗證 |
| 🚫 | 該領域的迷思 |

**第三欄「本領域的認定標準」是各 mentor 的核心差異，必須留在各自 SKILL.md，不得抽到這裡。**
各領域的鐵律（三條或四條）同理，不抽。

## §4 迷思雷達的處理格式

迷思**表格本身**屬各 domain，留在各自 SKILL.md。共用的只有命中之後的處理格式：

```
<符號> 你的問題包含一個常見的<領域>迷思：「<迷思內容>」
正確說明：<領域層面的解釋，含確定性符號>
這個迷思流傳的原因：<原因類型>
確認後，讓我繼續回答你真正的問題：<繼續展開>
```

`<符號>` 與 `<原因類型>` 見 §8。**時機一律是「回覆開頭優先指出，再展開正文」**，不是等使用者問。

## §5 知識圖譜節點區塊

```
【這個概念的位置】
<箭頭標籤組>

建議存入：knowledge/<domain>/<YYYY-MM-DD>-<主題>.md
```

`<箭頭標籤組>` 各 domain 不同（見 §8），但四個位置的語意固定：

| 箭頭 | 語意 |
|------|------|
| ↑ | 更基礎 / 先備 / 底層依賴 |
| ↔ | 同層並列 / 交叉 / 替代方案；已有筆記寫 `[[筆記名]]`，沒有寫 `[建議下一個節點]` |
| ↓ | 延伸 / 推導 / 上層應用 |
| × | 跨領域連結（指向其他 `knowledge/<domain>/`） |

## §9 維護規約

**改協定時的同步清單**（沒有任何自動檢查會擋你，這是純自律規約）：

```
[ ] 改本檔對應章節
[ ] 五份 mentor-*/SKILL.md 的「標準 mentor 協定」摘要區塊逐一同步
[ ] 改動涉及行為 → memory/project-context.md 追加 ADR
[ ] bash bin/token-budget.sh --strict
[ ] python3 bin/validate-skill-index.py
```

**新增第六個 mentor 時**：

1. 在 §8 表格加一欄，填滿七個變數；在 §11.2 加一欄，填滿六個維度（先填 §11.2 會逼你想清楚
   它和既有五個的差別在哪——填不出來就代表不需要新 mentor）
2. 在 §11.1 加該領域與鄰居最容易混淆的兩三列
3. 照既有 mentor 的結構寫 SKILL.md：`標準 mentor 協定摘要`（從 §8 展開）→ 角色定位 →
   思考路徑 → 領域確定性標準表 + 鐵律 → 回覆結構主體 → 迷思雷達表 → 觸發分流 → domain Checklist
4. **不要**把本檔的完整內容抄進新 SKILL.md——那是這次重構要消除的東西。
   §11 兩張表尤其不要抄回去：它們是維護者看的，執行時不需要（見 §10）
5. 走 `skills/convert-skill/SKILL.md` 流程更新 `skills/index.json` 與 `skills/llms.txt`，
   並在 `llms.txt` 的 mentor 判斷樹加一行——**那份才是實際生效的路由**

**明確不屬於本協定、不得往這裡搬的東西**：角色定位、思考路徑、各領域確定性標準、
鐵律、知識類型分類表、回覆結構的主體區塊、迷思雷達表格內容、「需主題確認」分流條款。
這些是各 mentor 的存在理由，抽掉就沒有專科 mentor 了。

## §10 觸發詞與路由表的冗餘（2026-08-18 識別，2026-08-21 處理完畢）

原分析：這些冗餘的省下幅度比 §1–§7 的骨架抽取更大，**且是無條件節省（不需要摘要換回去）**。

實際動手時發現冗餘是**三段**不是兩段——原分析寫的「與其他 mentor 的根本差異」表在【角色定位】段，
而它下方【觸發條件】段還另有一張路由表，兩者講同一件分工、格式卻不同：

| 冗餘段 | 位置 | 為什麼是冗餘 | 處置 |
|--------|------|------------|------|
| 「直接觸發」關鍵詞列表 | 【觸發條件】 | 這些詞已在 frontmatter `description` 裡，而 description 是**常駐在 system prompt** 的。SKILL.md 內這份要等 skill 載入後才被讀到——那時路由早已決定完畢，對任何決策零影響 | **五份全刪**，heading 改為【觸發分流】並在標題註明正本位置。同段的「需主題確認」分流條款有價值，全部保留 |
| 「與其他 mentor 的根本差異」表 | 【角色定位】 | 五張表比較對象各不相同（science 比 neuro+society、tech 比 science、society 比 neuro、neuro 比 academic-mentor、invest 比一個不存在的 mentor-business），彼此不一致；且每一列在該 SKILL.md 下方都有對應的正式段落 | **五張表刪除，合併為 §11.2** |
| 「與其他 mentor 的分工」路由表 | 【觸發條件】 | `skills/llms.txt` 的判斷樹已講同樣的分工，且那份才是實際生效的路由 | **五張表刪除，合併為 §11.1** |

**實測五份合計 55,404 → 50,620 bytes（−4,784，−8.6%；按 `token-budget.sh` 的 3.5 bytes/token
換算約 −1,370 tok）**，與原估的 ~1,600 tok 同一量級。刪掉 6,577 bytes，換上 1,742 bytes
（五個新 heading + 三份「本 skill 的界線」句 + society 併入的一行 + neuro 期刊清單併入【3】）。

- neuro 的「衝突時詢問」對話樣板——已經進到 skill 之後的執行時行為，不是路由決策

- tech 的「與 coding-workflow 的界線」——這是 tech 最高頻的邊界誤判，且 frontmatter description
  已寫了同一句話，留著與 description 一致；其【觸發分流】只用一行指回它，不寫第二份

neuro 原表獨有的「優先期刊 Nature Neuroscience / Neuron / PNAS」已併進【3. 文獻定錨】，未隨表消失。

## §11 跨 mentor 對照矩陣（原五份 SKILL.md 各自比較表的合併正本）

**執行時不載入。** 兩張表的作用對象都是**維護者**——路由在 skill 載入前就決定完了，實際生效的
是 frontmatter `description` 與 `skills/llms.txt` 的判斷樹；方法論差異則各自寫在該 mentor 的
確定性分級表、鐵律與回覆結構區塊裡。放在這裡是為了讓五個 mentor 的邊界有一份**彼此一致**的
定義可對照，新增第六個 mentor 時照這兩張表劃界。

### §11.1 路由矩陣（問題 → 哪個 skill）

**兩條劃界原則**（新增 mentor 時沿用）：

1. **同一個對象按抽象層切**，不按主題名稱切——多巴胺、社群媒體、AI 都同時出現在三個 mentor 裡，
   決定路由的是「問的是物質／機制／群體後果哪一層」
2. **概念層 vs 操作層**——要動程式碼走 coding-workflow / debug-flow，要具體數字走 tw-stock-tracker，
   mentor-* 一律只負責「為什麼」與「該怎麼選」

### §11.2 方法論維度矩陣（五個 mentor 為何不能互相取代）

原本五份 SKILL.md 各有一張「與其他 mentor 的根本差異」表，比較對象各不相同、彼此不一致
（science 比 neuro+society、tech 比 science、society 比 neuro、neuro 比 academic-mentor、
invest 比一個不存在的 mentor-business）。合併為單一矩陣後才看得出全貌：

| 維度 | neuro | society | science | tech | invest |
