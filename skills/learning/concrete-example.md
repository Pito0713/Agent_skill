# Concrete Example（具體情境舉例）

抽象邏輯轉成可逐步追蹤的具體情境，同時提供「正常解法」與「跳脫框架的替代解法」讓使用者選擇方向。

---

## 執行步驟

### Step 1：理解問題核心

```
[ ] 使用者卡在哪一個邏輯環節？
[ ] 這個邏輯的輸入是什麼、預期輸出是什麼？
[ ] 能從使用者的程式碼或訊息中抽取真實資料嗎？
    → 可以：用真實資料舉例
    → 不行：用具代表性的虛構資料
```

---

### Step 2：選擇最適合的呈現格式

依邏輯類型自動判斷：

| 邏輯類型 | 使用格式 |
|---------|---------|
| 時間計算、滑動窗口、累計計數 | 時間軸狀態表（逐行顯示每步狀態變化）|
| 條件判斷、多重 if/else | 決策路徑表（每個條件對應實際值與結果）|
| 資料轉換、filter/map/reduce | 輸入 → 中間步驟 → 輸出逐層對照 |
| 非同步、執行順序 | 時間序列圖（誰先執行、誰後執行）|
| 狀態流轉（訂單、流程） | 狀態機圖 + 實際資料走一遍 |
| 遞迴、巢狀結構 | 展開樹狀圖，逐層標示當前值 |

---

### Step 3：輸出兩個方案

---

#### 方案 A — 正常邏輯（沿用當前思路）

用具體資料走一遍正確的邏輯步驟：

```
情境說明：<一句話說明這個例子在模擬什麼>

[選擇的格式呈現，例如狀態表]

結論：
- 第 X 步是關鍵，因為 <原因>
- 程式碼對應位置：<指向具體的函式或行數>
```

---

#### 方案 B — 跳脫框架（換一種思路解決同一個問題）

當方案 A 的邏輯方向本身就容易出錯，提出完全不同的實作角度：

```
為什麼要跳脫框架：
<說明方案 A 的邏輯雖然正確，但在某些情境下容易誤用或難以維護>

替代思路：<用一句話說明不同的解法方向>

情境舉例：
[同樣的資料，用不同邏輯走一遍]

優缺點比較：
| 面向 | 方案 A | 方案 B |
|------|--------|--------|
| 易讀性 | ... | ... |
| 邊界條件 | ... | ... |
| 維護成本 | ... | ... |
```

---

### Step 4：詢問使用者

```
以上兩個方案，你想繼續走哪個方向？
或是哪個部分還不清楚，我可以再細化某一步？
```

---

## 輸出範例（時間軸狀態表）

**情境：7 天內通知量的滑動窗口計算**

```
日期       操作                 7天內通知量   說明
─────────────────────────────────────────────────────
6/1        通知 A 客人 3 件      3
6/3        通知 B 客人 2 件      5
6/8（今）  通知 C 客人 4 件      9
6/9（明）  6/1 的 A 超過 7 天    6            A 的 3 件滾出窗口
```

**結論**：滾出條件是「今天日期 - 通知日期 > 7」，6/9 檢查 6/1 時 9-1=8 > 7，所以 A 滾出。

---

## 注意事項

- 優先從使用者的訊息或程式碼抽取真實資料，讓舉例直接對應他遇到的問題
- 方案 B 不是否定方案 A，是提供思路選擇，使用者自己決定方向
- 每個例子只聚焦一個邏輯核心，不要同時解釋多個問題
- 如果使用者說「還是不懂」，縮小範圍，只舉一個最小的單一步驟
